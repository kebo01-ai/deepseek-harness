# Agent Note：一套能活过升级的部署皮肤

Status: implemented

[English](2026-11-08-deployment-skin-additive-seams.md) | 中文

## 问题

想要自己的名字、配色和字体的部署，没有一个以追加方式落地的地方。品牌面是侧栏的一对 slot 加对话空首屏的一个；其余的一切 —— 组件读的 token 阶梯、字体声明、标签页图标、安装清单、浏览器标题 —— 都在上游文件里，部署只能去改它们。

那些改动不是免费的。`master..upgrade/0.1.7-alpha.2` 在 `packages/client` 与 `apps/web` 下改写了 1783 个文件（+98002/−26318）。同一段区间里，以 slot 填充贡献同类面的 `ui-brand-official` 源码一行未动。靠上游改动承载的身份，在这种规模的每一次升级里都要人工读一遍；靠一个新目录和一行新 profile 配置承载的身份，根本不会被读到。

`ui-brand-official` 没法直接复用：它的第一条语句在 `DSH_CLIENT_BUILD_PROFILE` 不是 `official` 时就返回，所以它是一个由构建开关选中的身份，而不是部署可以自行组合的其中一个。

## 决定

`@deepseek-ai/dsh-client-ui-skin` 承载一个部署的视觉身份，它改动的每一个面都以追加方式供给：一个 slot 填充、一次主题 token 覆盖、一张追加在主题包自己那几张表之后的样式表，或者 Node 半边提供的一条路由。profile 用其 patch 末尾的一行 `- insert:` 挂载它，这让追加的那张表落在主题那六张之后，不用 `!important` 就拿到最后发言权。

四层，按升级要付的代价排序，一个面只有在上一层触及不到时才往下退：

1. **构建期环境变量** —— 任何 `DSH_CLIENT_*` 变量都经 `scripts/client-build-environment.ts` 透传，不需要逐个登记。`DSH_CLIENT_TITLE` 拥有浏览器标题；`DSH_CLIENT_BRAND_NAME` 是本包那个唯一的名字常量的缺省来源。
2. **本包** —— slot 填充、`ctx.theme.overrideTokens()`（落成 `body` 上的内联自定义属性，因此不与任何选择器比优先级）、追加的那张表，以及一条 `/_skin` 前缀路由，提供拼接后的 `@font-face` 样式表、该表点名的 `woff2` 文件、标签页图标和安装清单。
3. **profile overlay** —— `- insert:` 加一行，`disabled: true` 退一行。想整块换掉一个面，换掉渲染它的那个插件，而不是给它打补丁。
4. **上游补丁** —— 最后手段，每一笔都记在[部署皮肤补丁账](../../../../docs/skin-patches.zh.md)里，连同能删掉它的那条缝。

有三个面退到了第四层：空首屏的大标题，因为它是没有 slot 的 `t('hero.headline')`，而 locale 运行时给每个 namespace-locale 组合恰好一个所有者；启动闪屏的字标，因为闪屏在任何插件行加载之前就渲染；以及运行期许可闸门，它没有一类用于「交付资源而非代码」的依赖。

最后那一笔是值得点名的策略改动。`ASSET_ONLY_LICENSES` / `isAssetOnly` 放行 OFL-1.1，因为它的义务约束的是字体文件本身 —— 它们仍在 OFL-1.1 之下、带着自己的版权声明、不得以保留字体名重新分发 —— 而不约束与它们一同交付的任何东西。它刻意不去放宽 `PERMISSIVE_LICENSES`，那会把这条许可对以后每个依赖都重分类；也不去动用闸门已有的那条按身份授权的例外。

## 考虑过的替代方案

**设 `DSH_CLIENT_BUILD_PROFILE=official` 再改 `ui-brand-official`。** 那是一次构建一个身份，而不是一个部署一个身份；而且唤醒它会把本包的三个填充从品牌 slot 上挤掉。

**fork 掉 `dsh-client-ui-theme`，直接在源头改 token。** 这把那 1783 个文件的 diff 搬到 fork 上，每次升级都要重新解一遍 —— 正是上面那次测量反对的代价。

**要一个按 key 覆盖的 locale 能力，让空首屏大标题留在追加面。** `LocaleRuntime.register` 对重复的 namespace-locale 组合直接抛错，`lookup()` 取回退链上第一个有该 key 的 locale，因此后来的插件无法拥有一个它没注册过的 namespace 里的单个 key。那是一次上游改动；补丁账把它记成缺失的那条缝，而不是假装这笔补丁本可避免。

**把 `woff2` 拷进 `apps/web/public/fonts/`。** 客户端插件的 CSS 是当字符串注入的，里面的相对 `url()` 不会相对样式表解析 —— 这正是那条路由存在的原因。从路由提供也让字体字节留在已安装的包里而不是提交进本仓库，而且由样式表摘要导出的版本段让它们可以被 immutable 地提供，同时一次字体升级会让它们失效。

## 后果

这个身份是可以从浏览器里验的，不是声称的。两套主题下，`body` 上枚举出的 384 个自定义属性没有一个解析成蓝色，三个捆绑字族从路由加载且 Noto Sans SC 只取页面命中的那几片，图标与清单的链接指向 `/_skin`，标题来自 `DSH_CLIENT_TITLE`，`pageerror` 为空。`apps/web` 下没有改动任何文件：送出文档里的两处品牌链接是在出门时改写的，因为第二条图标链接会让浏览器在两者之间做选择。

设计本身带来两条限制。名字要设两遍 —— 浏览器包在构建时把 `DSH_CLIENT_BRAND_NAME` 烤进去，而 Node 半边在运行时读它 —— 因此改名的部署必须两处都设，只有共享的缺省值能自己保持一致。还有，字体经那条路由到达页面，因此不带 Web 服务器提供客户端的部署只会保留两条字体栈的平台尾部；那种情况下 Node 半边什么也不注册。

本包没有配置面。取值是源码，因此两个身份不同的部署需要两个包而不是两段配置 —— 这正是「让这个包加起来便宜」而不是「让它可配置」的用意。
